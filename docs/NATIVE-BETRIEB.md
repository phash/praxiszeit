# Native-Betrieb — PostgreSQL · Windows · SSL · systemd

Laufzeit-/Installations-/Betriebs-Regeln des **nativen** Einzelinstanz-Servers (`praxiszeit-server.py`, `installer/*`). **Nicht** App-Entwicklung — App-Regeln stehen in [CLAUDE.md](../CLAUDE.md), Build/Release in [BUILD-RELEASE.md](BUILD-RELEASE.md).

Übergreifende Pitfalls: [docs/NATIVE-WINDOWS-PITFALLS.md](NATIVE-WINDOWS-PITFALLS.md) · [docs/INSTALL-NATIVE.md](INSTALL-NATIVE.md).

## Modus & SSL
- **Native-Modus:** `SERVE_FRONTEND=True` → FastAPI liefert Frontend (nginx entfällt), `False` (Default) = Docker.
- **Self-signed SSL-Cert = End-Entity-Server-Cert in ALLEN 4 Generatoren (1.8.7):** Browser brauchen **RSA** (NICHT ed25519 — für TLS-Server-Certs nicht unterstützt → harte Ablehnung OHNE „Erweitert") + `basicConstraints=CA:FALSE` + `keyUsage` + `extendedKeyUsage=serverAuth` + Hostname im SAN. ⚠️ **Vier Stellen synchron halten:** `installer/linux/install.sh`, `ssl/generate-cert.sh`, `tools/generate-self-signed-cert.py` UND `_ensure_self_signed_cert()` in `praxiszeit-server.py` (Laufzeit-Auto-Generator = Default-Pfad für native Windows/macOS, wird leicht übersehen). macOS-Installer erzeugt gar kein Cert (HTTP).
- **SECRET_KEY persistieren:** Muss in `config/.secret-key` gespeichert werden, sonst Session-Verlust bei Restart.
- **cookie_secure:** Muss `false` sein ohne SSL, sonst lehnt Browser das Refresh-Cookie ab.
- **Nach Native-Update:** im Browser Hard-Refresh (`Ctrl+F5`) oder Service-Worker unregister, sonst bleibt das alte Frontend-Bundle im Cache.

## PostgreSQL (Native)
- **`psql/pg_dump immer mit `-w`:** sonst Endlos-Hänger an der Passwort-Abfrage im Dienst-/Headless-Kontext statt sauberem Fehler.
- **Native-Build verlangt `pg_env()`-Helper** in `praxiszeit-server.py` — alle 7 PG-Subprocess-Aufrufe (initdb, postgres, pg_ctl, psql, pg_dump) bekommen `env=pg_env()`, das `LD_LIBRARY_PATH=$BIN_DIR/postgresql/lib` (Linux/macOS) bzw. `PATH`-Prepend (Windows) setzt. Plus `PGHOST` auf `DATA_DIR/run/`, damit psql den umgezogenen Socket findet.
- **`unix_socket_directories` in `pg_init()`** muss auf `DATA_DIR/run/` zeigen (nicht `/var/run/postgresql`), weil systemd `ProtectSystem=strict` das default Verzeichnis read-only macht. Detail-Postmortem in #125.
- **Cluster-Marker `.praxiszeit-cluster`:** `pg_init` schreibt ihn in PGDATA. Daten-Dir OHNE Marker + ohne `.db-credentials` = fremd (EDB-Leftover) → wird zur Seite verschoben (`db.foreign-<ts>`, NIE gelöscht) + neu initialisiert; Bestands-Cluster mit Creds bekommen den Marker per Backfill.
- **Recovery bei verlorener `.db-credentials` (Native):** Marker da + Creds weg = scram-Cluster ohne Passwort → `cmd_start` failt fast mit Verweis auf `docs/INSTALL-NATIVE.md` Abschnitt "Disaster Recovery" (NIEMALS einfach `pg_setup_database` darauf loslassen — hängt/scheitert opak). Drei Pfade dort: (A) `.db-credentials` aus Backup zurückspielen, (B) `pg_dumpall` solange Cluster noch antwortet + `rm -rf data/db` + neu starten + restore, (C) nur Marker `data/db/.praxiszeit-cluster` entfernen → Quarantäne-Branch greift, altes Verzeichnis bleibt als `data/db.foreign-<ts>` erhalten. Tests: `test_native_pg_lifecycle.py::TestLostCredentialsFailFast`.
- **Native-Install — Host-Grenzen (1.8.0):** (a) **Rolling-Distros** (Arch/CachyOS): theseus-PG braucht `libxml2.so.2`, Arch ab libxml2 2.14 liefert nur `libxml2.so.16` → PG lädt nicht. `install.sh` hat `pacman`-Support + klaren Fail-Fast statt Crash-Loop; echter Bundle-Fix offen (#177). (b) **Vorhandene System-PostgreSQL auf :5432** (#174, **behoben 1.8.5**): Der native Cluster ist auf Unix jetzt **socket-only** (`pg_init` schreibt `listen_addresses=''`), Verbindung über den eigenen Unix-Socket in `DATA_DIR/run` via `_database_url()`; `pg_is_running()` probt den **eigenen Socket** statt TCP `localhost:5432`. Dadurch kollidiert ein **Neu-Install** nicht mehr mit einer fremden System-PG auf :5432 (auf .131 e2e verifiziert). ⚠️ **Bestands-Installs werden NICHT auto-migriert:** `pg_init` early-returned bei vorhandenem PGDATA, ihre `postgresql.conf` behält `listen_addresses='localhost'` (bindet also weiter TCP :5432). Sie sind nach dem Update trotzdem **erreichbar** (Socket in `DATA_DIR/run` existiert seit 1.5.0/#125 → `pg_is_running()`-Socket-Probe + `?host=`-URL treffen den eigenen Cluster, scram inkl.), aber die Koexistenz-Garantie gilt nur für Neu-Installs; eine *später* hinzukommende System-PG würde mit einem Bestands-Cluster weiter kollidieren (Tech-Debt: conf-Rewrite-on-upgrade, braucht Restart). **Windows unverändert** (kein Unix-Socket → bleibt TCP `localhost:5432`). ⚠️ Bei Änderungen am PG-Start/Connect immer **drei** Stellen zusammen pflegen: `pg_is_running()` + `_database_url()` + `pg_init`-`listen_addresses`.

## Dienststatus muss der Wahrheit entsprechen (#427)

`systemctl is-active praxiszeit` meldete `active`, während das Backend tot war. Drei Ursachen, alle behoben:

- **Eine fremde 200 galt als eigene Gesundheit.** Ist der Port belegt, beendet sich das eigene uvicorn sofort (`address already in use`) — die anschließende Gesundheitsprüfung bekommt aber trotzdem eine 200, nämlich vom **belegenden** Prozess (typischerweise eine zweite oder nicht gestoppte Installation). `wait_until_healthy()` prüft jetzt **zuerst** den Zustand des Kindprozesses und erst danach die HTTP-Antwort. Das ist die eigentliche Lücke; die Ticketbeschreibung vermutete den Fehler noch allein im weiterlaufenden Prozess-Manager.
- **Der Wachhund startete endlos neu.** `should_give_up()` beendet den Manager mit Exitcode 1, wenn sich uvicorn **5×** in **5 Minuten** beendet. Vorher lief der Manager weiter und hielt die Unit damit auf `active`, obwohl der Dienst in einer Absturzschleife steckte.
- **Belegter Port wird vorab erkannt.** `port_is_occupied()` (per `connect`, nicht per `bind` — ein Bind-Versuch auf einen privilegierten Port scheitert sonst an fehlenden Rechten und würde als „belegt" fehlgedeutet) meldet die Ursache als Klartext samt `ss -ltnp | grep :<port>`, bevor irgendetwas startet.

⚠️ **`StartLimitIntervalSec` / `StartLimitBurst` gehören in `[Unit]`, nicht in `[Service]`** — seit systemd 230 werden sie dort kommentarlos ignoriert. Ohne sie startet systemd trotz `Restart=on-failure` endlos neu und der Dienst erreicht nie `failed`. Gepflegt in **drei** Quellen: `installer/linux/praxiszeit.service`, `installer/linux/install.sh`, `installer/linux/install-local.sh`.

**macOS (launchd) bleibt vorerst wie es ist:** `KeepAlive=true` startet bedingungslos neu, einen ehrlichen `failed`-Endzustand wie bei systemd kennt launchd nicht. Der Exitcode des Managers ist jetzt zwar korrekt, ein Umbau auf `KeepAlive={SuccessfulExit=false}` bleibt aber ungetestet, solange keine Mac-Hardware zur Verfügung steht (siehe #183).

Tests: `test_native_pg_lifecycle.py::TestGesundheitspruefungGehoertZumEigenenKind` (inkl. Gegenprobe: dreht man die Prüfreihenfolge um, fällt der Test), `::TestAufgebenNachWiederholtenAbstuerzen`, `::TestPortVorabpruefung`.

## Kontoübernahme bei verlorenem Admin-Passwort (#425)

```
sudo praxiszeit-server.py reset-admin-password [--username admin] [--disable-2fa]
```

- Fragt das neue Passwort **interaktiv** ab (zweimal, gegen dieselbe Komplexitätsregel wie die Anwendung). **Bewusst kein Argument dafür** — es stünde in der Shell-History und in der Prozessliste.
- Erhöht `token_version` → alle bestehenden Sitzungen des Kontos werden ungültig.
- Startet die Datenbank bei Bedarf nur für die Dauer des Vorgangs und stoppt sie danach wieder, wenn sie vorher stand.
- **`--disable-2fa` ist der Hauptfall, nicht die Ausnahme:** ist auch der Authenticator verloren, verlangt der Login nach dem neuen Passwort weiterhin einen Code — ohne diese Option löst der Reset das Problem also nicht. Sie ist trotzdem ausdrücklich zu setzen: ein Passwort-Reset soll den zweiten Faktor nicht stillschweigend abschalten.
- Jeder Vorgang schreibt eine Zeile nach **`security_events`** (Art. 5 Abs. 2 DSGVO, Migration `071`) — `actor` trägt das Betriebssystem-Konto und den Rechner (`cli:<user>@<host>`), weil es hier kein handelndes Anwendungskonto gibt. **Nicht** in `time_entry_audit_logs`: das ist die §16-Domäne und über `row_hash` (#121) manipulationsgeschützt.
- Danach **entwertet** der Prozessmanager `[admin] password` in `config/praxiszeit.conf` (überschreibt den Wert mit einem Zufallswert, samt Kommentar). Der Eintrag war nur der Startwert der Erstinstallation, wird bei einer späteren Änderung **nicht** nachgeführt und steht dort dauerhaft im Klartext. ⚠️ **Der Schlüssel wird bewusst NICHT gelöscht:** `ADMIN_PASSWORD` ist in `app/config.py` ein Pflichtfeld **ohne Vorgabewert** — fehlt es, bricht die Anwendung beim nächsten Start schon beim Laden der Einstellungen ab, aus einem verlorenen Passwort würde ein toter Dienst. Der Ersatzwert ist zufällig und kein fester Platzhalter, weil `main.py` das Admin-Konto damit neu anlegen würde, sollte es irgendwann fehlen.
- **Kein neuer Angriffsweg:** wer Zugriff auf die Maschine hat, kommt über die rechtebeschränkte `config/.db-credentials` ohnehin an die Datenbank. Das Kommando macht daraus einen unterstützten und protokollierten Vorgang.
- Die Logik liegt im Backend (`app/cli/reset_admin_password.py`), damit sie Modelle, Passwort-Hashing und die Komplexitätsregel der Anwendung mitbenutzt statt sie nachzubauen. Der Prozessmanager reicht nur Umgebung und Argumente durch. Tests: `test_425_reset_admin_password.py`.
- **Mehrmandanten-Installation:** existiert derselbe Benutzername in mehreren Mandanten, bricht das Kommando ab statt zu raten.

## Windows-Installer (setup.bat / Wizard)
- **Native Windows-Fallstricke:** Siehe [docs/NATIVE-WINDOWS-PITFALLS.md](NATIVE-WINDOWS-PITFALLS.md) (psql -v, Glob-Expansion, SYSTEM-Permissions, cp1252, SPA-Routing).
- **setup.bat `DisableDelayedExpansion`:** Absicht (PowerShell-Passwort mit `!`). `%VAR%` in `(...)`-Blöcken wird beim Block-Parse substituiert → leere Vars erzeugen Syntax-Fehler (`if  GEQ 16`). Defaults vor dem Block setzen.
- **setup.bat PG-Reuse:** Existierende PG-Installation (Registry `HKLM\SOFTWARE\PostgreSQL\Installations` + `%ProgramFiles%\PostgreSQL\{14..18}`) wird bei Major ≥ 16 per `mklink /J` verlinkt statt neu installiert. `rd /s /q` folgt Junctions nicht → `uninstall.bat` bleibt sicher.
- **Windows VC++-Runtime (setup.bat `--install_runtimes 1`, ab 1.5.3/1.5.4):** EDB-PG-18-Binaries (MSVC) brauchen die VC++-Runtime, sonst `initdb.exe` Exit `0xC0000135` + NSSM-Crash-Loop. Erstinstall via `--install_runtimes 1`; In-Place-Update via `update-wizard.ps1`→`Step-VcRedist` (gebündelte `bin/vc_redist.x64.exe`, idempotent). `_check_pg_launchable()` übersetzt die NTSTATUS-Codes in eine klare Meldung. ⚠️ KEINE Klammern in setup.bat-`REM`-Zeilen im `()`-Block. Details + Sofort-Workaround → [docs/NATIVE-WINDOWS-PITFALLS.md](NATIVE-WINDOWS-PITFALLS.md) #11.
- **Windows: PostgreSQL läuft als eigener NetworkService-Dienst** (`pg_start` → `pg_ctl register -U "NT AUTHORITY\NetworkService"`), NICHT als Kindprozess — `postgres.exe` verweigert den Start unter dem LocalSystem-Token des NSSM-Dienstes. Unix: `pg_ctl start` (Kind) ok. `pg_ctl register` akzeptiert NUR `-N -D -U -P -S -e -W -t -s -o` (kein `-l`, kein lowercase `-w`).
- **NetworkService braucht Schreibrecht auf `data\db` UND `logs\`** — `postgresql.log` (logging_collector) liegt in `logs\`. Ein Update kann diese ACL zurücksetzen → `FATAL: could not open log file … Permission denied` → PG startet nicht (hat eine Produktion lahmgelegt, 1.5.x). `pg_start` (Windows) grantet beides jetzt vor jedem Start idempotent (`icacls … *S-1-5-20 …`). Recovery bei Bestands-Installs: `icacls C:\PraxisZeit\logs /grant "*S-1-5-20:(OI)(CI)F" /T`. PG-Start-Timeout ist 60s (error-487/ASLR-Retries auf manchen Maschinen).
- **Robocopy im Update-Wizard merged ohne Purge:** stale Files in `bin/python/Lib/site-packages/` kumulieren über Updates hinweg. `Step-PipInstall` bootstrappt pip deshalb via `get-pip.py --force-reinstall` VOR `pip install -r requirements.txt` (F-056). Gleiches Pattern wenn weitere `bin/`-Subdirs im Wizard behandelt werden.

## Linux-Installer / systemd
- **`installer/linux/install.sh` installiert Runtime-Libs automatisch** (`libxml2 libssl3 libgssapi-krb5-2 libzstd1 liblz4-1 libreadline8 libbrotli1` via apt-get/dnf/zypper). Auf Ubuntu-Minimal-Images sind die nicht alle da, theseus' postgres-Binary linkt aber dagegen.
- **`install.sh` / systemd-Unit (Debian-Cloud-Härtung, ab 1.8.0):** Native-Service läuft als **non-root** (`User=<svc>`, `NoNewPrivileges=yes`). Privilegierte Ports (<1024, z. B. 443) → `install.sh` vergibt für `PORT < 1024` automatisch `AmbientCapabilities=CAP_NET_BIND_SERVICE` + `CapabilityBoundingSet=…` (sonst `bind … permission denied`, Feldreport). Tägliches Backup läuft jetzt über einen **systemd-Timer** (`praxiszeit-backup.timer/.service`) statt `crontab` — cron fehlt auf Minimal-Images (Debian-13-Cloud: `crontab: command not found`). Zusätzliche Hardening-Direktiven in der Unit (`ProtectKernel*`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `RestrictNamespaces` …) — `RestrictAddressFamilies` muss `AF_UNIX` enthalten (PG-Socket in `DATA_DIR/run/`). Linux-/macOS-Tarball entpackt **flach** (`build-release.sh`: `tar -czf … -C "$DIR" .`, kein Top-Level-Ordner) → `INSTALL-NATIVE.md` extrahiert deshalb mit `-C <ordner>`. ⚠️ `validate-release.sh` + `validate-macos.yml` setzen das flache Layout voraus (`cd /opt/pz && tar xzf …`) — Tarball-Struktur NICHT auf Top-Level-Ordner umstellen, ohne beide Validatoren anzupassen.
- **Installer-Shell: kein `cmd | grep -q` / `| head` unter `set -o pipefail` (1.8.8):** `grep -q`/`head` beenden früh → linke Pipe-Seite bekommt SIGPIPE (141) → `pipefail` macht die Pipeline non-zero → `if !` schlägt um bzw. `$()`+`set -e` killt den Installer. Tritt NUR auf Hosts mit vielen Libs/langer Ausgabe auf (Desktops/Server), NICHT in Minimal-Containern → `validate-release` maskiert es. Stattdessen: Variable + Here-String (`grep -q … <<<"$var"`) oder `awk 'NR==1'`. Gilt für `installer/linux/install.sh` UND `installer/macos/install.sh`.
